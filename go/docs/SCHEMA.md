# PostgreSQL item schema

The Go API owns `go/migrations/`. Apply migrations with Goose before starting the API. `goose_db_version` records applied versions. Do not edit an applied migration; add a new one.

`items.id` is the existing 32-character lowercase hexadecimal identifier generated by the Go service. It remains the primary key and the public API ID. `title` and `description` are required text columns with length checks matching the API limits. `creation_order` is a generated bigint used for the API's creation-order list. The primary key and unique creation-order constraint provide the needed indexes. No extension is required.

The HTTP boundary rejects blank titles and counts Unicode characters before writing. Database constraints protect stored data if another writer bypasses the API. PostgreSQL's `btrim` check rejects ordinary blank-space titles; the API's Unicode whitespace check is stricter. Create, replace, and delete each use one atomic SQL statement. All queries bind item values as parameters.

The first migration's `Down` step refuses to remove a nonempty `items` table. For a populated database, roll back the application while keeping the additive table, or write a reviewed forward-repair migration. A database dump and verified restore are required before any planned data removal. Use a separate migration role with schema-changing privileges; the application role needs only `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on `items` plus sequence usage for `creation_order`.

For later changes, prefer additive columns and constraints that work while old and new API versions overlap. Check existing data before tightening constraints. On a populated production table, plan indexes according to lock impact; `CREATE INDEX CONCURRENTLY` cannot run inside a transaction and needs explicit failure cleanup.
